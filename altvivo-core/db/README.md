# altvivo-core/db — database layer: paid access, billing, CMS and the audit engine

PostgreSQL 16 schema for `db_core`, managed with Prisma 5.22 plus raw-SQL migrations for everything Prisma can't express.

```
db/
├── schema.prisma                                    Prisma models (27 tables, 23 enums)
├── migrations/
│   ├── 20261114000000_init/                         base tables (generated by prisma migrate diff)
│   ├── 20261114000100_integrity_audit_security/     audit hash chain, credit ledger, CHECKs, grants
│   └── 20261115000000_paid_access_billing_cms/      strict paid access, payments, GST invoices, advisory board,
│                                                    contact, consent (enum rework maps existing data)
├── seed/seed.ts                                     idempotent: audit genesis, app registry, price list
├── scripts/
│   ├── deploy.mjs        npm run db:deploy        migrate → seed.ts → SYSTEM.DB_DEPLOY audit event → verify chain
│   ├── verify-audit.mjs  npm run db:verify-audit  recompute the hash chain (exit 2 = tampering)
│   └── run-tests.mjs     npm run db:test          integrity + least-privilege suite (rolled back)
└── tests/integrity.test.sql
```

## Strict paid access

There is no free tier and no trial. `user_access_claims(user_id [, at])` returns one row per registered app (`app_id, app_status, active, source, plan_code, plan_kind, expires_at`); altvivo-core turns it into the JWT `entitlements` claim and `/v1/auth/verify` answers from that claim.

`active` is true only while a paid grant is in force:

| Grant | Source | In force while |
|---|---|---|
| Single-app subscription (`xprism_*`, `amaze_*`) | `individual` | status `ACTIVE`/`PAST_DUE` and `current_period_start ≤ now < current_period_end` |
| Dual-Suite bundle (`suite_*`) | `bundle` | same |
| Site licence (`site_license_annual`, per seat) | `institution` | same, for members with a verified e-mail of an `ACTIVE` organization |
| Manual licence by a SUPERADMIN (NEFT / RTGS / PO) | `manual` (user) or `institution` (org) | not revoked and `starts_at ≤ now < expires_at` |

- **Never active:**
  - a disabled user;
  - a `PENDING`, `CANCELED` or `EXPIRED` subscription;
  - a `PAST_DUE` subscription past its paid period (no grace).
- **Several grants for one app.** The longest-lasting grant is reported.
- **VIP roles.** `SUPERADMIN` and `ADVISORY_BOARD` get nothing extra here: altvivo-core applies their bypass (`PAID_GATE_VIP_ROLES`).
- **Subscription rows.** Subscription-derived `app_entitlements` rows are materialised by triggers from `plan_entitlements`, both when a subscription is created or changes plan and when an admin edits a plan's app list. The runtime role cannot write them.
- **Manual licences** (`source = MANUAL`):
  - Granted only by an active SUPERADMIN, with a reason and a mandatory expiry.
  - Expiry, reason and reference can be edited until the licence is revoked.
  - Revoked with `revoked_at` and `revoke_reason`; never deleted.
- **Ownership rules.** Site licences must belong to an organization, and single-app and bundle plans to a user. Seat counts must fall within the plan's `min_seats`/`max_seats`.
- **Seats.** Each active (not disabled) member of an organization uses one seat. A join beyond `seat_limit` is rejected under a row lock. `seat_limit` cannot drop below the active members.

## Money, payments and GST invoices

- **Units.** Amounts are integer minor units (paise / cents).
- **What includes GST.** Plan prices and `subscriptions.unit_amount_minor` (the price frozen at purchase, per seat for `PER_SEAT` plans) exclude GST. Payments include it.
- **`payments`**: online (Razorpay INR, Stripe) and `BANK_TRANSFER` (needs `reference` and `recorded_by`).
  - Status machine: `CREATED → AUTHORIZED → CAPTURED → PARTIALLY_REFUNDED → REFUNDED`, with `FAILED` reachable only before capture.
  - Payer, currency and amounts are immutable.
  - Processor ids and the capture time are set once.
  - Refunds only grow.
  - Rows are never deleted.
- **`invoices` + `invoice_lines`**: tax invoices (`AV/2026-27/00042`), proformas for procurement (`PF/…`), and credit notes (`CN/…`).
  - **Snapshots.** Seller and buyer details are copied into the invoice when it is created.
  - **Tax maths.** Line amounts and header totals are computed by triggers from quantity, unit price, discount and the GST rate (basis points). Rounding is half-up per line. Totals are re-derived from the lines at issue, so header totals written directly never reach an issued invoice.
  - **Treatments:**
    - `INTRA_STATE`: CGST + SGST; place of supply = seller state = buyer state.
    - `INTER_STATE`: IGST; place of supply = buyer state ≠ seller state.
    - `EXPORT`: zero-rated under LUT; place of supply `96`; buyer outside India; INR or USD.
  - **GSTIN validation.** GSTINs are checked for format and mod-36 checksum, and for state-code consistency.
  - **Lifecycle:**
    - `DRAFT` is editable and deletable.
    - Issuing assigns the next gapless number for the kind and Indian financial year (IST, from 1 April). The number comes from `invoice_series`, which only the definer trigger can write. A rolled-back issue releases its number.
    - After issue every field is frozen except settlement and the one-time PDF key and hash.
    - `ISSUED → PAID | CANCELLED`. A paid tax invoice is reversed with a credit note, never cancelled.
    - Credit notes need a referenced tax invoice and cannot exceed its total.
    - A proforma needs a `valid_until` date.
- **`revenue_active_subscriptions`**: per-subscription period amount and MRR (GST-exclusive) for the admin revenue dashboard. ARR = 12 × MRR.

## Site content

- **`advisory_board_members`**: the CMS behind `/advisory-board` and the homepage section.
  - Visibility flags: `is_published` and `featured`; ordering: `sort_order`.
  - URLs are https-only. Scholar and LinkedIn URLs are pinned to their domains, so a `javascript:` or look-alike link is rejected.
  - A photo needs alt text.
  - ORCID format is checked, and there are at most 12 specialization tags of 60 characters each.
  - Linking `user_id` does not change the account's role.
- **`contact_messages`**: `POST /v1/public/contact`, with a fixed category list.
- **`consent_records`**: append-only cookie-consent evidence (DPDPA 2023 / GDPR Art. 7(1)).
  - Rows are keyed by the random id in the first-party consent cookie.
  - The IP is stored only as a peppered SHA-256 hash.
  - `ACCEPT_ALL` and `REJECT_NON_ESSENTIAL` must match their category flags.
  - Update and delete are rejected even for the owner.

## Audit engine (21 CFR Part 11)

- **Server-assigned fields.** A `BEFORE INSERT` trigger assigns `id`, `timestamp`, `previous_hash` and `record_hash`, discarding whatever the caller sent. `id` comes from `audit_logs_id_seq` while the trigger holds a row lock on `audit_chain_head`, so id order equals chain order.
- **Hash.** `record_hash = SHA-256(jsonb_build_array(id, ts_utc_µs, actor_type, actor_id, actor_ip, user_agent, app_id, event_type, resource_id, metadata, previous_hash)::text)`. The first record links to `AUDIT_CHAIN_GENESIS`.
- **Append-only, two layers.** `UPDATE`/`DELETE`/`TRUNCATE` are revoked from `core_app`, and triggers reject them even for the table owner. The chain head can only advance and its genesis is immutable.
- **Tamper evidence.** `audit_verify_chain(from, to)` detects altered, inserted, deleted, reordered and tail-deleted rows, even after triggers were disabled by a superuser.
- **Who / where.** Call `SELECT audit_set_context(actor_id, ip, user_agent, app_id, actor_type)` at the start of each transaction.
- **Automatic row-change audit.** `DB.<TABLE>.<OP>` events, with an old/new diff and secrets redacted, cover users, organizations, oauth_accounts, mfa_recovery_codes, app_registry, plans, plan_entitlements, subscriptions, app_entitlements, workspace_files, payments, invoices, invoice_lines, billing_profiles and advisory_board_members.
- **Keep audit transactions short.** The head lock serialises audit writers until commit.

## Credits

The ledger is unchanged. Insert `{user_id | org_id, app_id, action_type, delta, reference_id}`; the trigger locks the account, computes `balance_after`, and rejects overdrafts (`23514`) and duplicate references (`23505`). `credit_balance_for_user()` feeds the `credits_remaining` claim.

## Roles

| Role | Can |
|---|---|
| `core_migrator` | own the schema, run migrations and the seed |
| `core_app` | DML, except: no UPDATE/DELETE on `audit_logs`, `credit_ledger`, `consent_records`; no writes to `audit_chain_head`, `credit_accounts`, `invoice_series`; no DELETE on `payments`, `app_entitlements`, `workspace_files`, `billing_events`; no subscription-derived entitlement writes; cannot draw invoice numbers; no access to `_prisma_migrations` |
| `core_readonly` | SELECT for reporting, including `revenue_active_subscriptions`. No credential, session, billing-profile, contact or consent tables (use `users_directory`); can run `audit_verify_chain()` |

## Seed (`seed.ts`)

Idempotent, one serializable transaction, run by `db:deploy` (or alone with `npm run db:seed`). It is plain TypeScript run natively by Node ≥ 22.18.

- **Audit genesis.** Created once. A run with a different `AUDIT_CHAIN_GENESIS` fails.
- **App registry.** `xprism` and `amaze` are seeded `LIVE` (the only applications). The old `COMING_SOON` status is refused by `app_registry_no_coming_soon_chk`. Re-runs refresh the catalogue copy but never the status or version.
- **Price list.** Created only when a plan is missing, so later `/admin` edits survive. Prices exclude GST; SAC 997331, 18 %.

| Plan | Kind | INR | USD |
|---|---|---|---|
| `xprism_monthly` / `xprism_annual` | single app | ₹1,499 / ₹14,990 | $24 / $240 |
| `amaze_monthly` / `amaze_annual` | single app | ₹1,999 / ₹19,990 | $29 / $290 |
| `suite_monthly` / `suite_annual` | Dual-Suite bundle | ₹2,999 / ₹29,990 | $45 / $450 |
| `site_license_annual` | site licence, per seat, min 25 | ₹2,400 / seat / year | $60 / seat / year |

Advisory board members, institutions and users are real people and organisations, so the seed creates none. Enter them in `/admin`; SUPERADMIN accounts come from `npm run cli:create-superadmin`.

AUDIT_VERIFY_DATABASE_URL=postgresql://core_readonly:...@postgres:5432/db_core npm run db:verify-audit

ALTVIVO_ALLOW_DB_TESTS=1 TEST_MIGRATOR_URL=... TEST_APP_URL=... TEST_READONLY_URL=... npm run db:test

Schema changes: edit `schema.prisma`, then run `npm run db:migrate:dev -- --name <change>` against a development database. Put raw SQL (triggers, grants) in that new migration. Check for drift with `prisma migrate diff --from-url <migrated db> --to-schema-datamodel db/schema.prisma --exit-code`. Never edit an applied migration.
